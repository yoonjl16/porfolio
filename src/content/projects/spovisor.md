## 문제

야구·축구·배구 경기를 보러 다른 지역에 가는 팬이 많지만, 경기 **앞뒤 시간에 경기장 근처에서 무엇을 할지**는 직접 검색해서 맞춰야 합니다. 일반 여행 추천은 경기 시작 시간, 경기장 위치, 동행자, 이동수단 같은 **직관 여행만의 조건**을 고려하지 않습니다.

## 해결

사용자가 경기장과 여행 조건을 설문으로 고르면, 경기 일정에 맞춘 **서로 다른 대안 코스 3개**를 시간표와 함께 추천합니다.

- **설문 항목** — 경기장, 여행 방식(경기 전/후), 이동수단, 최대 이동 시간, 동행, 컨셉(미식 탐방형 · 관광지 중심형 · 로컬 힐링형), 추가 조건(예: 혼잡 피하기), 꼭 넣을 장소, 제외 조건
- **지원 범위** — 전국 프로스포츠 경기장 69곳을 지역 코드와 좌표로 매핑
- **피드백 재추천** — 코스의 장소에 좋아요·싫어요를 누르면 취향을 반영해 바로 다시 추천

## 추천 모델

### 8차원 취향 벡터

사용자와 장소를 같은 8차원 벡터(미식 · 힐링 · 체험 · 레포츠 · 문화 · 자연 · 역사 · 혼잡선호)로 표현해 **코사인 유사도**로 비교하는 콘텐츠 기반 추천입니다.

- **사용자 벡터** — 컨셉별 기본 벡터에 동행 유형 보정(예: 가족여행 → 체험·자연 가산, 혼자 여행 → 혼잡선호 감산)과 추가 조건을 더해 생성
- **장소 벡터** — 관광지 카테고리(역사·문화·자연·레저·체험·쇼핑 등)별 기본 벡터에 **지역 특성 가중치**를 곱해 생성. 같은 "자연관광"이라도 자연 수요가 높은 지역에서는 점수가 더 높아집니다
- **지역 벡터** — TourAPI의 지역별 관광 수요 지표 코드(9개)를 벡터 차원으로 매핑해 계산

### 후보 필터링

- 이동수단별 반경(도보 2km · 대중교통 5km · 자차 15km) 밖의 장소, 제외 카테고리, 좌표가 없는 장소를 제거
- 연관 관광지 API로 음식점 후보를 추가하고, "혼잡 피하기"를 고르면 혼잡도 예측 API로 감점
- 접근성 조건(무장애 여행 등)이 있으면 무장애 관광지 API로 거름
- "꼭 넣을 장소"(고정핀)는 모든 필터에서 예외로 처리해 반드시 포함

### MMR 코스 다양화

비슷한 코스 3개를 주면 선택지가 없는 것과 같습니다. 그래서 **MMR(Maximal Marginal Relevance)** 방식으로 대안 코스를 만들었습니다.

1. 컨셉별 비율(맛집 · 관광지 · 자연 · 쇼핑)에 맞춰 카테고리마다 장소 개수를 나눔
2. 장소를 하나씩 추가하면서 **코스 전체의 평균 벡터**가 사용자 벡터와 가장 비슷해지는 장소를 고름 (혼잡을 피하려는 사용자는 혼잡한 장소일수록 감점)
3. 앞서 만든 코스와 장소가 **50% 넘게 겹치면** 겹치지 않는 후보로 교체
4. 같은 카테고리가 연속되지 않도록 순서를 조정 (예: 식당 → 식당 방지)

### 일정 배정

- 경기 시작 전 도착 시간과 장소별 체류 시간을 기준으로 각 장소에 **방문 시각**을 배정
- 두 좌표 사이 거리(하버사인 공식)를 이동수단별 속도로 나눠 이동 시간을 추정
- "경기 전/후" 선택에 따라 경기장을 코스 중간이나 끝에 고정하고, 여러 날 일정도 생성

### 피드백 반영

좋아요를 누른 장소의 벡터 쪽으로 사용자 벡터를 이동하고, 싫어요는 반대로 이동합니다(학습률 0.05). 이후 정규화해 바로 재추천합니다. 사용자 벡터는 응답에 담아 보내고, 다음 요청 때 다시 받아 이어서 업데이트합니다.

## 데이터 · API 연동

| 용도 | API |
| --- | --- |
| 지역 관광 수요 지표 (지역 벡터) | TourAPI 지역별 관광 수요 |
| 지역 중심 관광지 후보 | TourAPI 기초지자체 중심관광지 |
| 연관 관광지 · 음식점 | TourAPI 연관 관광지 |
| 혼잡도 | TourAPI 관광지 집중률 예측 |
| 무장애 여행 정보 | TourAPI 무장애 여행 |
| 좌표 · 출발지 검색 | Kakao Local API |

TourAPI 응답(XML)을 실시간으로 받아 파싱하고, Kakao 좌표 검색 결과는 장소명 기준으로 캐시해 같은 장소를 반복 조회하지 않게 했습니다. 코스 요약 문구는 LLM 없이 **슬롯 템플릿**으로 생성해 응답 속도와 비용을 줄였습니다.

## 서버

- Flask API: `POST /recommend` (설문 → 코스 3개), `POST /feedback` (좋아요·싫어요 → 재추천), `GET·POST /survey` (마지막 설문 불러오기·저장)
- Docker 이미지로 패키징, API 키는 환경변수(`.env`)로 분리
- 백엔드 연동을 위한 API 명세와 체크리스트를 README로 정리

## 배운 점

- **추천의 "다양성"도 설계 대상이다** — 정확도만 높이면 비슷한 코스만 나왔습니다. 유사도와 중복도를 함께 따지는 MMR을 넣고 나서야 실제로 고를 수 있는 대안이 되었습니다.
- **공공 데이터를 모델의 입력으로 쓰려면 매핑이 핵심이다** — TourAPI 지표 코드를 취향 차원에, 경기장을 지역 코드에 연결하는 작업이 모델 로직만큼 중요했습니다.
