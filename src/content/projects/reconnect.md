## 문제

연인 관계에서 갈등은 대개 두 사람의 **애착 유형 차이**(예: 확인을 원하는 불안형 vs 거리를 원하는 회피형)에서 생깁니다. 하지만 일반적인 연애 조언은 한 사람 기준이라 **커플 두 사람에게 동시에 맞는 실천 방법**을 주기 어렵습니다. 또 하루하루 달라지는 관계 상태도 반영하지 못합니다.

## 서비스 흐름

1. 두 사람이 매일 애착 문항(총 36일치)에 응답합니다
2. 응답을 바탕으로 그날의 **불안·회피 점수**와 애착 유형(안정·불안·회피·혼란)을 계산합니다
3. 추천 엔진이 커플에게 **오늘의 조언 1개**를 추천합니다 (예: "호흡 3분: 서로 말없이 숨만 함께 맞춰보세요")
4. 두 사람이 조언에 좋아요·싫어요를 남기면 바로 다음 추천에 반영됩니다
5. 기간이 끝나면 변화 추이와 맞춤 실천 방법을 담은 **최종 리포트**를 만듭니다

## 추천 알고리즘

### UBCF → Item-CF로 전환

처음에는 사용자 기반 협업 필터링(UBCF)으로 설계했습니다. 하지만 UBCF는 **비슷한 다른 사용자의 기록이 미리 있어야** 동작합니다. 사용자가 없는 서비스 초기에는 추천을 할 수 없는 콜드 스타트 문제가 생깁니다. 그래서 조언끼리의 유사도를 **미리 계산해 둘 수 있는 Item-CF**로 바꿨습니다.

### 점수 계산

- **아이템 표현** — 조언 50개를 임베딩 벡터로 나타내고 L2 정규화, 조언 간 코사인 유사도 행렬을 계산
- **KNN 이웃 제한** — 아이템마다 가까운 k개 이웃만 남겨 노이즈와 과적합을 줄임
- **필터링** — 이미 본 조언, 블랙리스트, "싫어요"를 받은 조언은 후보에서 제외
- **애착 유형 보정** — 애착 유형별 선호 태그를 매핑해 두고, 후보 조언의 태그와 겹치면 점수 가산
- **최근 피드백 보정** — 최근 좋아요·싫어요를 받은 조언의 태그와 겹치면 가산·감산

### 커플 합의 추천

A와 B의 점수 벡터를 각각 계산(애착 보정과 피드백 반영 포함)한 뒤 **같은 가중치로 평균**해, 두 사람 모두에게 맞는 조언 1개를 고릅니다. 추천 결과에는 근거(reason)와 유사한 이웃 조언도 함께 담겨 "왜 이 조언인지" 설명할 수 있습니다.

### 실시간 업데이트

피드백이 들어오면 상호작용 행렬(`csr_matrix`)을 다시 만들고, 사용자 취향 벡터를 **EMA**로 업데이트합니다. 좋아요는 해당 조언 쪽으로 끌어당기고(α=0.25) 싫어요는 밀어냅니다(β=0.15).

## LLM 리포트

- **일일 리포트(IR)** — 오늘의 문항, 두 사람의 불안·회피 점수 변화, 애착 유형 분포, 추천 조언에 한 줄 해석·강점·이슈를 붙여 JSON으로 생성
- **최종 리포트(FR)** — 기간 전체의 점수 변화(처음 대비), 함께 할 소통 실천, 각자 맞춤 행동 조언, 바로 쓸 수 있는 대화 스크립트를 생성
- **안정적인 생성** — `gpt-4o-mini`를 사용하고, 출력 JSON 스키마에 버전(`schema_version`)을 붙여 프론트엔드와 맞췄습니다. tenacity 재시도와 응답 캐시로 API 실패와 비용에 대비했습니다
- **점수 블렌딩** — 설문 점수와 GPT가 자연어 답변을 채점한 점수를 섞어 하루치 점수를 보정했습니다

## 백엔드 연동

추천 엔진을 실제 서비스에 붙일 수 있도록 **DB 스키마와 API 명세를 직접 설계해 백엔드에 전달**했습니다.

- 테이블: `advice_items`, `advice_embeddings`(pgvector), `advice_similarity`, `user_feedbacks`, `daily_states`, `sessions`
- API: `GET /recommend/ir/top1?scope=couple|member` (추천 조회), `POST /feedback` (좋아요·싫어요 전송), 기준 데이터 업로드용 관리자 API

## 배운 점

- **데이터가 없는 초기 상태를 먼저 고려해야 한다** — 알고리즘의 정확도보다, 사용자가 없을 때도 동작하는지가 서비스 초기에는 더 중요한 기준이라는 걸 UBCF → Item-CF 전환으로 배웠습니다.
- **추천 결과는 설명 가능해야 한다** — 관계 조언처럼 민감한 영역에서는 "왜 이 조언인가"를 함께 보여줘야 사용자가 받아들인다고 판단했고, 그래서 근거와 유사 조언을 출력에 넣었습니다.
- **명세를 명확히 해야 협업이 빠르다** — 모델 코드만 넘기지 않고 JSON 스키마, DB 테이블, API까지 문서로 정리해 백엔드에 전달했습니다. 입출력 형식을 먼저 약속해 두면 각자 따로 개발해도 쉽게 맞춰 붙일 수 있다는 걸 배웠습니다.
